## 1. Critical — "Run fast probe" unpins your model and can brick chat

**Symptom.** Clicking **Run fast probe** in the sidebar replaces the pinned model with a cloud model the user never selected. If the probe fails, every subsequent chat is rejected with HTTP 409 and there is no UI control to recover.

**Cause.** The button hardcodes its target and ignores the current pin:

```js
// gateway/static/index.html:974
body: JSON.stringify({ provider: "openrouter", name: "openai/gpt-4o-mini", mode: "fast" })
```

`/api/probe` then writes the probe's own target into settings as the new pin:

```python
# gateway/app.py:350-352
store.set_setting("card", json.dumps(card))
store.set_setting("model_pin", json.dumps(card["model_pin"]))   # <- overwrites the user's pin
store.save_card(card)
```

**Reproduction.** Observed against the live server:

```
BEFORE: pin: ollama / af-unsloth-llama-3-2-1b-instruct-gguf:latest | card.verdict: agent
        POST /api/probe {"provider":"openrouter","name":"openai/gpt-4o-mini","mode":"fast"}
AFTER:  pin: openrouter / openai/gpt-4o-mini                       | card.verdict: chat_only
```

With no key the probe cannot succeed, so `verdict` is always `chat_only`. Set any key and the gate at `gateway/app.py:695-697` then rejects everything:

```
POST /api/chat -> HTTP 409 {"detail":"probe verdict chat_only: timeout"}
```

**Why it looks harmless in casual testing.** Without a key, `/api/chat` hits the `_prefer_local_ollama` fallback and re-pins a local model on the next message, hiding the damage. The failure only becomes permanent for users who *do* have a key — the exact users the button is aimed at.

**Fix.**
- Probe the currently pinned model, not a hardcoded one. Send the pin from `/api/health`, or have `/api/probe` default to the active pin when the body omits a name.
- Do not let `/api/probe` mutate `model_pin`. Probing should measure the pin, not replace it. Separate "measure" from "select".
- Give the UI a way out of a `chat_only` card — a "clear verdict" / "re-probe" affordance, or scope the gate so a failed probe warns instead of hard-blocking.

## 2. Critical — failed Ollama pulls report success and pin a model that does not exist

**Symptom.** Pulling a nonexistent or misspelled tag shows a completed 100% download, tells the user "Using \<tag\> on this folder.", and pins it. The next message fails with a raw provider stack trace.

**Cause.** Ollama returns **HTTP 200** and reports failure *inside* the NDJSON stream:

```
POST http://127.0.0.1:11434/api/pull  -> 200
{"status":"pulling manifest"}
{"error":"pull model manifest: file does not exist"}
```

`_pull_worker` parses each event but never inspects `ev.get("error")`. `raise_for_status()` passes, the stream ends normally, and the worker unconditionally declares success:

```python
# gateway/runtime/ollama_runtime.py:126-129
with _JOBS_LOCK:
    _JOBS[job_id]["status"] = "success"
    _JOBS[job_id]["percent"] = 100.0
    _JOBS[job_id]["done"] = True
```

**Reproduction.**

```
POST /api/catalog/pull {"name":"definitely-not-a-real-model-xyz", ...}
GET  /api/catalog/pull/e72646206ad8
  -> {"status":"success","percent":100.0,"log":"pulling manifest\n\n","error":null,"done":true}

UI:            "Using definitely-not-a-real-model-xyz on this folder."
GET  /api/health -> model.name = "definitely-not-a-real-model-xyz"
POST /api/chat   -> HTTP 502
   litellm.APIConnectionError: OllamaException - {"error":"model '...' not found"}
```

The model is absent from `/api/tags` throughout. The user's previously working pin is gone.

**Fix.**
- Treat any streamed event carrying `error` as a job failure: set `status="error"`, record `ev["error"]`, stop.
- Verify the tag is present in `/api/tags` before reporting success and before pinning.
- Do not pin on the strength of a pull result alone — pin only after the tag resolves.

The same class of bug applies to a stream that is cut short mid-download: the loop exits cleanly and reports 100%.

## 3. High — eval grader hardcodes the demo fixture word `demurrage`

**Symptom.** Correct answers are stamped with a red `enumeration recall 0 · FAIL incomplete_enumeration` banner.

**Cause.** When the question has no explicit `mention <term>`, the grader falls back to a literal lifted from the sample corpus, and the trigger is an unanchored substring test:

```python
# gateway/evals.py:68-71
m = re.search(r"mention(?:ing)?\s+(\w+)", question, flags=re.I)
if m or "list" in question.lower():
    term = m.group(1) if m else "demurrage"
    enum = enumeration_recall(index, term, paths)
```

`"list" in question.lower()` matches inside ordinary words. Rendered at `gateway/static/index.html:1024`.

**Reproduction.** Verified directly against `score_run`:

| Question | Graded against | Result |
|---|---|---|
| `List the files in this folder.` | `demurrage` | FAIL |
| `Give me the check**list** for berth windows` | `demurrage` | FAIL |
| `Can you **list**en to my request and summarise DOC-002?` | `demurrage` | FAIL |
| `Show me a play**list**` | `demurrage` | FAIL |
| `What is the account total in DOC-001-NEPTUNE.txt?` | not graded | pass |

In a real customer folder the word `demurrage` is usually absent, so `truth` is empty and `enumeration_recall` returns `recall 1.0` — the check silently passes for the wrong reason. Where the word *does* appear (shipping, chartering — this product's stated domain) users get bogus failures on unrelated questions.

**Fix.**
- Drop the `demurrage` fallback. Grade enumeration only when a term is actually extracted from the question.
- Match `list` on a word boundary (`\blist\b`) rather than as a substring.
- Note: `enumeration_recall`'s empty-truth early return omits the `precision` key its other branch sets (`gateway/evals.py:32-40`). No consumer reads it today, so this is latent, not live.

## 4. High — files added after launch are listed but invisible to search

**Symptom.** Drop a document into the workspace; it appears immediately under "Workspace files" but no search can find it. Nothing in the UI explains why.

**Reproduction.**

```
$ echo "... Unique marker: quintessorial ..." > $WS/DOC-013-ZEPHYR.txt
GET /api/files            -> DOC-013-ZEPHYR.txt present
idx.search('quintessorial')  -> []
idx.grep_paths('quintessorial') -> []      # stale grep.json — the eval ground truth is stale too

POST /api/ingest          -> {"files_scanned":13,"chunks":13}
idx.search('quintessorial')  -> ['DOC-013-ZEPHYR.txt']
```

**Cause.** The fix already exists on the backend and is simply not wired to anything:

```
$ grep -c 'api/ingest"' gateway/static/index.html
0
```

The UI references only `/api/ingest/warnings`. `README.md` frames CLI-only ingest as intentional ("decision b"), but that decision predates the sidebar listing files live — the file list now advertises documents the agent cannot see.

**Fix.** Add a "Re-index" button in the sidebar calling the existing `POST /api/ingest`, or detect the mismatch (files on disk vs. chunks indexed) and surface a prompt. Also invalidate the cached `grep.json` on re-ingest so the scorer's ground truth stays in step.

## 5. High — llmfit browse opens on 11,271 models, none of them usable

**Symptom.** "Browse llmfit models" — listed first among the model CTAs — opens a catalog where every visible card is disabled with *"no GGUF files in HuggingFace repo; try a \*-GGUF repo"*.

**Reproduction.** Default `sort=score`, sampled across the catalog:

| offset | states | downloadable |
|--------|--------|--------------|
| 0 | 80 × `UNRESOLVABLE` | 0 / 80 |
| 400 | 80 × `UNRESOLVABLE` | 0 / 80 |
| 2000 | 80 × `UNRESOLVABLE` | 0 / 80 |
| 6000 | 80 × `UNRESOLVABLE` | 0 / 80 |

Downloadable entries do exist — `?q=GGUF` returns 51 matches, 46 of them `gguf_downloadable: true` — but the user has to guess that search term. `/api/catalog/llmfit` (`gateway/app.py:409-421`) exposes `q`, `provider`, `use_case`, `capability`, `fit`, `sort`, `tools` — no filter on `state` or `gguf_downloadable`.

Once you find one, the rest of the flow is sound: download → `ollama create` → pin completed successfully end to end.

**Fix.**
- Default the modal to downloadable rows only, and add a visible "Downloadable / All" toggle backed by a new `state`/`downloadable` query param.
- Rank `NO_RUNTIME` (downloadable) above `UNRESOLVABLE` in the score sort so the first page is actionable.
- The **Download** tab in the sidebar is permanently empty for the same reason (`PULLABLE` is never produced) and its own empty-state text admits it. The **All** tab is 80 of 87 rows disabled. Consider collapsing the three tabs until there is something to put in them.

## 6. Medium — llmfit import tag mismatch breaks the active-model highlight

After an llmfit download the pin is the bare tag while Ollama reports the `:latest` form:

```
pin:          af-unsloth-llama-3-2-1b-instruct-gguf
/api/tags:    af-unsloth-llama-3-2-1b-instruct-gguf:latest
```

The comparison is exact (`gateway/static/index.html:393, 421-422`):

```js
card.className = "card" + (pinName === currentPin ? " active" : "");
use.textContent = pinName === currentPin ? "Using" : "Use in this folder";
```

So after every llmfit download **no** card shows "Using" — all seven rows rendered an enabled "Use in this folder", and the sidebar no longer indicates which model is active. Chat still works, because Ollama resolves bare names to `:latest`.

**Fix.** Normalise both sides (append `:latest` when no tag is present) before comparing, in `renderCatalog` and in `_row_for` (`gateway/app.py:445`), which does the same exact match to gate `NO_RUNTIME`/`UNRESOLVABLE` and silently no-ops when it misses.

## 7. Medium — ANSI escapes and a doubled percentage in download progress

The raw llmfit CLI line is stored as the job status without sanitising:

```python
# gateway/llmfit_download.py:61
job["status"] = line.strip()[:80] or job["status"]
```

and the UI appends a second, differently-rounded percentage to a line that already contains one:

```js
// gateway/static/index.html:768
const line = (p.status || "downloading") + (p.percent ? " " + Math.round(p.percent) + "%" : "");
```

Rendered to the user, verbatim from the DOM:

```
"\u001b[K  66.2% - Downloading 0.5/0.8 GB 66%"
```

The `\x1b[K` erase-line escape shows as a box glyph, and the same progress is stated twice with two different numbers.

**Fix.** Strip ANSI (`re.sub(r"\x1b\[[0-9;]*[A-Za-z]", "", line)`) before storing. Either show the parsed `percent` or the CLI's own text, not both.

**Related:** the llmfit download has no Cancel button even though `POST /api/catalog/llmfit/download/{job_id}/cancel` exists and works. Downloads are ~1 GB and uninterruptible from the UI.

## 8. Medium — token meter compares incompatible numbers

```js
// gateway/static/index.html:1028
meter.textContent = `tokens ${u.prompt_tokens || 0} / ${u.max_tokens || 32000} · ...`;
```

`u.prompt_tokens` is the **cumulative** session total from the store; `u.max_tokens` is the **per-turn** budget from the spec. The loop's enforcement (`gateway/runtime/loop.py:261-264`) checks `state["tokens"]`, which resets to 0 every `run_loop`. The header therefore presents a budget bar that will read `40000 / 32000` and keep going — nothing stops at the line it draws. Observed at `tokens 15991 / 32000` after two messages.

Separately, `store.add_usage(session_id, turn, 0, usd)` always passes 0 for completion tokens, so the whole turn total accumulates under the `prompt_tokens` label and `completion_tokens` is permanently 0.

**Fix.** Either enforce the cumulative budget, or label the meter as per-turn and show cumulative separately. Pass the real completion count.

## 9. Medium — re-pinning fabricates the measurement it is supposed to derive

`stats.py` is built around never trusting the mean — `max_steps` and `max_tools` come from the Wilson **lower** bound. Two paths bypass it by writing a literal:

```python
# gateway/app.py:147 and gateway/app.py:551
"measured": {"per_step_success_lo95": 0.5, "max_tools": 3, "max_steps": 3},
```

Any pin selected without a probe — which is every "Use in this folder" click — gets an invented 0.5 that then feeds `max_steps_from_lo95` and every `score_run` result. Every eval trace captured in this pass reported exactly `per_step_success_lo95: 0.5`.

**Fix.** Mark unprobed pins as unmeasured (`lo95: None`) and have the budget math fall back to a documented conservative default, so a fabricated number is never mistaken for a measured one.

## 10. Medium — `schema_reject` reaches the user as internal jargon

The 1B models the sidebar labels "tools" routinely call `fs_list` with `rag_search`'s arguments. 4 of 4 attempts on *"Which files mention demurrage?"*:

```json
{"kind":"tool","tool":"fs_list","args":{"query":"demurrage","limit":80},"error":"schema_reject"}
```

The user sees: **"The fs_list step failed: schema_reject"**, and the run dead-ends.

Two problems: the message is internal vocabulary from the `FAILURES` taxonomy with no English rendering on this path, and no recovery is attempted even though `{query, limit}` exactly matches `rag_search`'s schema and the question is precisely the retrieval case. `wants_file_list` (`gateway/runtime/loop.py:139-153`) covers `"list every"` and `"what files"` but not `"which files"`, so the fallback never fires either.

**Fix.** Translate `schema_reject` into plain English. When rejected args validate against a sibling tool's schema, re-dispatch there. Add `"which files"` to `wants_file_list`.

## Low

- **API key at rest.** `openrouter_key` is stored plaintext in `<workspace>/.agentforge/app.sqlite`, mode `-rw-r--r--`, inside the document folder the user pointed the tool at — a folder plausibly synced to OneDrive/Dropbox or shared. No endpoint echoes it back (verified across `/api/health`, `/api/models`, `/api/permissions`, `/api/later`, `/api/scan`, `/api/usage`, `/api/ingest/warnings`), and `.agentforge/` is gitignored *in this repo* — but not in an arbitrary `--dir` that happens to be a git repo.
- **Raw enum leaks into the UI.** `"fits " + r.FITS` (`gateway/static/index.html:355`) renders "fits wont_fit" and "fits unknown". Casing is inconsistent between sources — "fits good" for merged Ollama rows, "fits Good" for llmfit rows — in the same list.
- **Fit is computed from instantaneous free RAM.** `gateway/catalog.py:255` prefers `available_ram_gb` over `total_ram_gb`, so a 1.9 GB model reads "wont_fit" on a 31.7 GB machine and the label flips between page loads (observed 1.4 / 2.19 / 2.72 GB free across three reads).
- **Wrong empty state when filtering.** Filtering the Ready tab to zero matches says *"No installed local models. Open Download to pull one, or use OpenRouter above."* — with seven installed. The message is keyed on the tab, not on whether a filter is active.
- **No "New chat" / clear-session control.** Session state accumulates in `default` forever; the only reset is deleting `app.sqlite`.
- **`GET /favicon.ico` 404s** on every page load — the only console error in the whole pass.
- **llmfit modal layout.** The "Load more" footer overlaps and clips the last row; the modal header wraps "Browse llmfit models" onto two lines beside a full-width "Close" bar.
- **No responsive breakpoint.** The sidebar stays ~290 px at a 720 px viewport, squeezing the chat pane. Acceptable for a localhost desktop tool; noted for completeness.

## What works

Confirmed good, so it does not get re-tested from scratch next time:

- **Path traversal is solid.** `../../../../Windows/win.ini`, URL-encoded variants, absolute `C:\Windows\win.ini`, and `.agentforge/app.sqlite` all correctly rejected with 400.
- **Write permissions.** `deny` / `ask` / `allow` persist correctly; invalid values rejected with 400. The `ask` flow produces a proper confirm token with a unified diff, and the extension allowlist and backup-before-replace policy behave as documented.
- **Ollama browse modal.** 9 models, correct `Using` state, working pull for real tags, correct fit badges.
- **llmfit download happy path.** Search → download → `ollama create` → auto-pin completed end to end (`Imported as af-unsloth-llama-3-2-1b-instruct-gguf`).
- **Chat export, file download, ingest warnings, catalog filter and `tools only`, the three catalog tabs** all behave as intended.
- **CORS** is correctly pinned to the concrete `127.0.0.1`/`localhost` origin for the chosen port rather than `*`.
- **No JavaScript errors** anywhere in the session beyond the favicon 404.

## Answering "will it work for everyone?"

Not yet. Walking the ordinary first-run paths:

| First-run path | Outcome today |
|---|---|
| Paste OpenRouter key, click **Run fast probe** (a prominent sidebar button) | If the probe fails for any reason — bad key, rate limit, network blip — **every chat 409s from then on**, with no UI recovery. §1 |
| Click **Browse llmfit models** (the first model CTA) | Dead end: 11,271 models, nothing on screen is downloadable. §5 |
| Typo a tag in the Ollama **Pull tag** field | Reported as a successful 100% download; pinned to a model that does not exist; next message 502s. §2 |
| Drop a new PDF into the folder | Shows in the file list, invisible to the agent, no way to re-index from the UI. §4 |
| Ask "list the files in this folder" | Correct answer stamped with a red `FAIL incomplete_enumeration`. §3 |
| Install Ollama first, pick a Ready model, ask a question | Works. |

The last row is the path that works, and it is the one most likely to have been exercised during development.

## Suggested fix order

1. **§1** and **§2** — both silently destroy working state and both are small, well-localised changes.
2. **§4** — the backend fix already exists; it needs a button.
3. **§3** — one-line fallback removal plus a word-boundary anchor.
4. **§5** — a filter param and a sort tweak.
5. **§6–§10** — correctness and polish.
6. **Add regression tests.** The suite is at 142 green with all of the above present. At minimum: a probe that must not mutate `model_pin`; an `/api/pull` stream carrying `{"error": ...}` that must fail the job; `score_run` on `"playlist"` that must not grade.
